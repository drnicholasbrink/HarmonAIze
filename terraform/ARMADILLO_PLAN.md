# HarmonAIze — Federated Analysis Stack (Armadillo / DataSHIELD / Keycloak)

Architecture, design decisions, and the **post-deploy checklist** for the optional analysis tier
(`deploy_analysis_stack = true`). This is the doc referenced by
[`DEPLOY_RUNBOOK.md`](./DEPLOY_RUNBOOK.md) Phase I.

> Commands are PowerShell-friendly but shell-agnostic. Defaults assume `prefix=harmonaize`,
> `environment=prod` → resource group `harmonaize-prod-rg`, VM `harmonaize-prod-analysis-vm`.
> `$RG = terraform output -raw resource_group_name`; `$KV = ((terraform output -raw key_vault_uri) -replace 'https://','').Split('.')[0]`.

---

## 0. Design decisions

### 0.1 Key decisions
- **Single-VM Docker Compose**, not AKS. The analysis tier is low-traffic and stateful (Armadillo
  storage + Keycloak DB); a VM with `docker compose` is far cheaper and simpler than a cluster.
- **Private VM, no public IP.** The VM sits in the `analysis` subnet (`10.0.8.0/24`) at a fixed
  `10.0.8.4`. Inbound is NSG-restricted to `8080/8081` from the Container Apps subnet and from
  `analyst_source_cidrs`. Egress (image pulls) is via a **NAT Gateway**.
- **Secrets generated by Terraform, fetched at boot.** All passwords + the OIDC client secret are
  random-generated into Key Vault; the VM's managed identity reads them at first boot. No secret is
  ever in the image, the compose file, or Terraform variables.
- **Config shipped via Storage, not baked in.** `docker-compose.analysis.yml`, `application.yml`,
  `Armadillo.json` (Keycloak realm), and `profiles.json` are uploaded to the `analysis-config`
  blob container and pulled by cloud-init — so config changes don't require rebuilding anything.
- **Idempotent first-boot.** cloud-init mounts the data disk, installs Docker, fetches config +
  secrets (**with retry** for RBAC propagation — see `modules/analysis_vm/cloud-init.sh`),
  substitutes realm placeholders, and runs the stack. It runs once per OS-disk lifetime.

### 0.2 What gets deployed
| Component | Detail |
| :--- | :--- |
| VM | `Standard_D2s_v3`, Ubuntu 22.04, private IP `10.0.8.4`, user-assigned identity |
| Data disk | Premium_LRS 128 GB (LUN 10) → `/data-disk` (ext4), symlinked `/app/data` |
| Networking | `analysis` subnet + NSG, NAT Gateway + public IP (egress only), `harmonaize.internal` DNS zone, A-record `armadillo → 10.0.8.4` |
| Stack (compose) | `armadillo 3.2.0` (`:8080`) · `rock-base 6.2-R4.3` R server (`:8085`) · `keycloak 25.0.2` (`:8081`) · `postgres 16` (Keycloak DB) |
| Key Vault secrets | `armadillo-admin-password`, `keycloak-admin-password`, `keycloak-db-password`, `rock-admin-password`, `rock-user-password`, `armadillo-oidc-client-secret`, `analysis-vm-ssh-private-key` |
| Bastion (opt-in) | `deploy_bastion = true` → `AzureBastionSubnet` (`10.0.9.0/26`), Standard public IP, Bastion host, NSG rule allowing SSH from Bastion |

## 1. Post-deploy checklist

### 1.1 Verify the stack came up
The VM has no inbound SSH by default; use the control plane (no network path needed):
```powershell
az vm run-command invoke -g $RG -n harmonaize-prod-analysis-vm `
  --command-id RunShellScript `
  --scripts "cd /app && docker compose -f docker-compose.analysis.yml ps; echo '---'; tail -n 60 /var/log/cloud-init-output.log"
```
Expect all four services **Up** (Keycloak healthy after ~1–2 min). If a service is missing, read the
cloud-init log for the failed step.

### 1.2 (Optional) interactive SSH via Bastion
Deploy with `deploy_bastion = true`, then retrieve the generated key and connect:
```powershell
az keyvault secret show --vault-name $KV --name analysis-vm-ssh-private-key --query value -o tsv > analysis_vm_key.pem
# Standard SKU (native client):
az network bastion ssh -n harmonaize-prod-bastion -g $RG `
  --target-resource-id $(terraform output -raw analysis_vm_name) `
  --auth-type ssh-key --username azureuser --ssh-key analysis_vm_key.pem
# Basic SKU: connect from the Azure Portal → VM → Connect → Bastion (paste the key).
```
Delete the local key file afterwards.

### 1.3 Give analysts a working path to the OIDC hostname  ⚠️ most common failure
Keycloak and Armadillo are configured on `http://armadillo.harmonaize.internal:8080/:8081`.
That name resolves **only inside the VNet's private DNS**. Analysts connecting from
`analyst_source_cidrs` can reach `10.0.8.4` (NSG allows it) but their browsers can't resolve the
name, so the **OIDC redirect breaks**. Give them one of:
- a hosts-file entry: `10.0.8.4  armadillo.harmonaize.internal`, **or**
- DNS forwarding for `harmonaize.internal` over the VPN (e.g. an Azure DNS Private Resolver +
  conditional forwarder).

> For production with real data, front the VM with TLS (reverse proxy) and a routable hostname,
> then update the canonical URL in `Armadillo.json` + the URIs in `application.yml` and re-import
> the realm. Today the stack is plain **HTTP** on a private name — acceptable only inside a trusted network.

### 1.4 Create analyst accounts in Keycloak
Open `http://armadillo.harmonaize.internal:8081` (admin / `keycloak-admin-password` from Key Vault),
realm **Armadillo** → create users / group mappings. The HarmonAIze app can sync some of this
(`ANALYSIS_KEYCLOAK_SYNC_ENABLED=true`); initial roles and any non-app users are manual.

### 1.5 Create Armadillo projects and load data
The stack starts empty. Either drive it from the HarmonAIze app's project-export flow, or upload via
the Armadillo UI/API at `:8080` (admin / `armadillo-admin-password`). End-to-end check: trigger a
project export from the app → confirm the object appears in Armadillo → have an analyst run a
DataSHIELD call.

### 1.6 Confirm the DataSHIELD profile + package versions
The `default` profile (`application.yml`) whitelists `dsBase` on `rock-base:6.2-R4.3`. Verify the
profile is **Online** in Armadillo (Profiles tab) and that the server has `dsBase` loaded. Analysts
must install a **matching client** (`dsBaseClient` for 6.2 / R 4.3) — client/server version skew is
the #1 cause of `ds.*` errors. Add more server packages by extending `package-whitelist` and the
profile image, then re-uploading the config blob and recreating the stack.

### 1.7 Turn the app integration on (if the VM was added later)
With `deploy_analysis_stack = true`, the compute module injects `ANALYSIS_ENABLED=true`, the
`ANALYSIS_ARMADILLO_*` / `ANALYSIS_KEYCLOAK_*` URLs, and the admin-password secrets into the
web/worker apps. If you enabled the stack **after** the first app deploy, run `terraform apply` and
roll a new revision so those land:
```powershell
az containerapp update -n harmonaize-prod-web -g $RG --revision-suffix "r$(Get-Date -UFormat %s)"
```

## 2. Backup & deallocate model

- **Persistent data** lives on the Premium data disk (`/data-disk`): `armadillo/` (project data) and
  `keycloak-db/` (realm + users). The OS disk holds `/app` (config + `.env`).
- **Cost control — deallocate when idle.** `az vm deallocate -g $RG -n harmonaize-prod-analysis-vm`
  stops billing for compute; both disks persist, and `az vm start` brings the stack back (cloud-init
  does **not** re-run, so config/data survive). Bastion (if deployed) bills separately — delete it
  when not needed.
- **Backup.** No automated backup is configured. Add a disk snapshot schedule (Azure Backup or a
  scheduled `az snapshot create` on the data disk) before loading real data. The Keycloak Postgres
  volume is inside the data disk, so a disk snapshot captures both data + auth state consistently
  when taken with the VM stopped.

## 3. Updates & secret rotation
- **Image upgrades**: edit `harmonaize/compose/production/analysis/docker-compose.analysis.yml`,
  re-upload it (Terraform does this automatically on the next apply via `azurerm_storage_blob`), then
  on the VM `cd /app && docker compose pull && docker compose up -d`.
- **Rotate a password / OIDC secret**: update the secret in Key Vault, then re-run the relevant
  cloud-init steps on the VM (re-fetch secret, rewrite `.env` / re-substitute `Armadillo.json`,
  `docker compose up -d`). cloud-init does not re-run on its own.

## 4. Troubleshooting
| Symptom | Likely cause | Action |
| :--- | :--- | :--- |
| A container is missing in `docker compose ps` | cloud-init step failed | Read `/var/log/cloud-init-output.log` via `az vm run-command` |
| cloud-init aborted fetching secrets | KV/Storage RBAC not yet propagated | The script now retries ~5 min; if still failing, confirm the VM identity has *Key Vault Secrets User* + *Storage Blob Data Reader*, then `az vm run-command` re-run `cloud-init` or reboot |
| OIDC login redirect fails / "can't reach armadillo.harmonaize.internal" | analyst can't resolve the private name | §1.3 — hosts entry or DNS forwarding |
| `ds.*` calls error | client/server DataSHIELD version skew, or profile offline | §1.6 — align `dsBaseClient`, check the profile is Online |
| Can't SSH to the VM | no public IP and Bastion not deployed | Use `az vm run-command` (§1.1) or set `deploy_bastion = true` (§1.2) |
| App can't reach Armadillo | `ANALYSIS_ENABLED` still false / app not re-applied | §1.7 |
